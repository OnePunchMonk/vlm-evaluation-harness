⏺ Here's a comprehensive table of post-training regressions across foundation
  model types:

  Post-Training Regressions Matrix

  Foundation Model: LLM (Decoder-only)
  SFT (Supervised Fine-Tuning): Alignment tax: drop in general
    knowledge/reasoning after narrow-domain SFT. Catastrophic forgetting of
    pre-trained capabilities. Loss of multilingual ability when SFT'd on
    English-only data.
  RLHF / PPO: Reward hacking: model exploits reward model flaws (verbosity,
    sycophancy). Mode collapse: reduced output diversity. Alignment tax  on
    coding/math benchmarks.
  DPO / Preference Optimization: Likelihood displacement: probability mass
  shifts
     away from correct but "unpreferred" completions. Reduced calibration. Less
    severe mode collapse than RLHF but still measurable.
  Quantization (INT8/INT4): Perplexity degradation (especially INT4). Long-tail
    knowledge loss. Outlier token failures on rare vocabulary. Reasoning chain
    breakdowns on multi-step problems.
  Distillation: Capacity gap: student fails on long-context reasoning teacher
    handles. Distribution shift on OOD inputs. Loss of emergent abilities (e.g.,

    CoT reasoning).
  Pruning / Sparsification: Lottery ticket instability: unpredictable capability

    loss. Degradation on low-resource languages first. Factual recall degrades
    before fluency does.
  LoRA / Adapter Tuning: Task interference when multiple adapters merged.
    Catastrophic forgetting (less than full SFT but still present).
    Rank-deficient updates miss complex capability  shifts.
  ────────────────────────────────────────
  Foundation Model: VLM (Vision-Language)
  SFT (Supervised Fine-Tuning): Modality imbalance: vision grounding degrades
    when SFT focuses on text quality. Hallucinated  spatial relationships. Loss
    of fine-grained visual understanding.
  RLHF / PPO: Vision reward blindness: reward model under-weights visual
    correctness → model hallucinates objects. Text-vision misalignment
  increases.
  DPO / Preference Optimization: Similar to RLHF but visual grounding errors are

    harder to capture in preference pairs. Annotator  bias toward text quality
    over visual accuracy.
  Quantization (INT8/INT4): Cross-modal alignment collapse: vision-language
    binding degrades at low precision. Small object  detection failure.
    OCR/text-in-image reading breaks at INT4.
  Distillation: Cross-modal bottleneck: student loses fine-grained vision-text
    associations. Spatial reasoning degrades faster than object recognition.
  Pruning / Sparsification: Connector layer sensitivity: pruning vision-language

    connector causes disproportionate quality loss. Modality dropout — model
    ignores image entirely.
  LoRA / Adapter Tuning: Modality-specific forgetting: vision adapter updates
    degrade language, and vice versa. Adapter routing  conflicts in multi-task
    settings.
  ────────────────────────────────────────
  Foundation Model: Diffusion Models (Image)
  SFT (Supervised Fine-Tuning): Mode collapse / style homogenization: model
    converges to narrow aesthetic. Concept bleeding: fine-tuned concepts leak
    into unrelated prompts. Loss of compositional generation.
  RLHF / PPO: Reward over-optimization: images become "hyper-aesthetic" but
    anatomically wrong. Diversity collapse — limited poses, compositions.
  Texture
     washing (over-smoothed outputs).
  DPO / Preference Optimization: Preference bias amplification: over-saturated
    colors, centered compositions. Reduced prompt  adherence for unusual/complex

    prompts.
  Quantization (INT8/INT4): Banding artifacts in gradients. Detail loss in
    high-frequency textures (hair, fabric). Color accuracy shift. Denoising 
    instability at low step counts.
  Distillation: Fidelity ceiling: student model produces blurry/over-smoothed
    outputs. Loss of rare concept generation. Step-distilled models fail on
    complex compositions.
  Pruning / Sparsification: Structural coherence loss: hands, faces degrade.
    Background artifacts. Fine detail generation (text rendering, small objects)

    fails first.
  LoRA / Adapter Tuning: Concept entanglement: LoRA concepts interfere with base

    model concepts. Overfitting to training style with few-shot LoRA. Subject
    identity leakage across prompts.
  ────────────────────────────────────────
  Foundation Model: Diffusion Models (Video)
  SFT (Supervised Fine-Tuning): All image diffusion regressions plus: temporal 
    flickering introduced. Motion incoherence — objects teleport between frames.

    Scene consistency degrades.
  RLHF / PPO: Temporal reward hacking: individual frames look good but motion is

    unnatural. Static bias — model learns to minimize motion to avoid penalties.
  DPO / Preference Optimization: Preference data is temporally sparse → model
    optimizes single-frame quality over temporal coherence. Motion quality 
    regression.
  Quantization (INT8/INT4): Frame-to-frame inconsistency amplified. Temporal 
    aliasing artifacts. Motion smoothness degrades before  per-frame quality
    does.
  Distillation: Motion complexity loss: student generates simpler, shorter
    motions. Temporal coherence gap — harder to distill than spatial quality.
  Pruning / Sparsification: Temporal layer sensitivity: pruning temporal
    attention causes disproportionate motion degradation.  Scene transition 
    failures.
  LoRA / Adapter Tuning: Temporal overfitting: LoRA learns motion patterns from
    limited data, causing repetitive/looping motion artifacts.
  ────────────────────────────────────────
  Foundation Model: Speech / Audio Models
  SFT (Supervised Fine-Tuning): Speaker identity loss after content-focused SFT.

    Prosody flattening. Accent/dialect erasure. Domain narrowing (e.g., loses
    music understanding  after speech SFT).
  RLHF / PPO: Naturalness-intelligibility tradeoff: optimizing for preference
  can
     reduce clarity. Emotional range collapse.
  DPO / Preference Optimization: Preference bias toward standard accents/voices.

    Reduced expressiveness in TTS.
  Quantization (INT8/INT4): Audio artifacting: clicking, buzzing at low
  bitwidth.
     Pitch accuracy degradation. Phoneme confusion on similar-sounding words.
  Distillation: Speaker diversity loss. Prosodic flattening in student models.
    Reduced ability to handle noisy/reverberant audio.
  Pruning / Sparsification: Frequency band loss: pruned models lose
    high-frequency detail first. Background noise  handling degrades.
  LoRA / Adapter Tuning: Voice leakage between adapter-tuned speakers. Narrow 
    acoustic adaptation — fails outside fine-tuned acoustic conditions.
  ────────────────────────────────────────
  Foundation Model: Multimodal Generative (e.g., any-to-any)
  SFT (Supervised Fine-Tuning): All single-modality regressions plus:
  cross-modal
     coherence loss — modalities become internally consistent but mutually
    inconsistent. Modality  favoritism toward SFT data's dominant modality.
  RLHF / PPO: Multi-objective reward conflict: optimizing one modality's quality

    degrades another's. Alignment fragmentation across modalities.
  DPO / Preference Optimization: Preference annotation is modality-biased
    (annotators evaluate text quality more reliably than audio/image alignment).
  Quantization (INT8/INT4): Inter-modal synchronization failure: e.g., lip-sync
    breaks in audio-visual generation. Worst-case modality dominates overall
    quality.
  Distillation: Cross-modal binding failure: student loses ability to maintain
    semantic consistency across modalities. Emergent cross-modal  abilities lost
   
    first.
  Pruning / Sparsification: Pruning must be modality-balanced or weakest
  modality
     collapses entirely. Shared representations are disproportionately
  sensitive.
  LoRA / Adapter Tuning: Adapter composition explosion: combining per-modality
    adapters creates unpredictable interference patterns.

  Key Takeaway Patterns

  1. Forgetting is universal — every post-training method trades off some
  pre-trained capability, but the what varies by method
  2. Cross-modal methods are fragile — VLMs and multimodal models suffer
  regressions at modality boundaries that unimodal models don't face
  3. Quantization hits rare/complex capabilities first — common tasks survive;
  long-tail knowledge and multi-step reasoning degrade
  4. RLHF/DPO regressions are behavioral (mode collapse, reward hacking) while
  quantization/pruning regressions are structural (artifacts, precision loss)
  5. Temporal models (video, audio) are especially sensitive because coherence
  across time is harder to preserve than per-frame/per-token quality

⏺ Short Answer: No — this unified framework doesn't exist yet.

  There are partial solutions covering fragments of the problem, but nothing
  that works as the "pre-flight checklist" you're describing. Here's the
  landscape:

  ---
  What Exists Today (Partial Coverage)

  Tool / Framework: EleutherAI's LM Eval Harness
  What It Does: Benchmark suite to measure regressions after training
  What It Doesn't Do: No predictive capability before training
  ────────────────────────────────────────
  Tool / Framework: Hugging Face TRL (+ PEFT)
  What It Does: Provides SFT/DPO/RLHF recipes with known-good defaults
  What It Doesn't Do: Doesn't diagnose your specific regression risks upfront
  ────────────────────────────────────────
  Tool / Framework: OpenAI's Evals / Inspect AI (AISI)
  What It Does: Structured eval frameworks
  What It Doesn't Do: Post-hoc measurement, not pre-training prescription
  ────────────────────────────────────────
  Tool / Framework: Scaling laws research (Chinchilla, etc.)
  What It Does: Predicts loss given compute/data/params
  What It Doesn't Do: Doesn't predict capability-specific regressions from
    post-training
  ────────────────────────────────────────
  Tool / Framework: Task Arithmetic / Model Merging (Ilharco et al.)
  What It Does: Theory for how task vectors interfere
  What It Doesn't Do: Narrow — only covers weight-space composition, not
    data/objective design
  ────────────────────────────────────────
  Tool / Framework: Forgetting metrics (e.g., Backward Transfer in CL
  literature)
  What It Does: Measures catastrophic forgetting
  What It Doesn't Do: Continual learning frameworks exist but don't generalize
    well to modern LLM post-training
  ────────────────────────────────────────
  Tool / Framework: PEFT method selectors (LoRA rank sweeps, adapter configs)
  What It Does: Help pick efficient fine-tuning config
  What It Doesn't Do: No regression-aware recommendation engine

  ---
  Why It Doesn't Exist (Yet)

  The problem is genuinely hard for several compounding reasons:

  1. Regressions are emergent and task-specific — You can't predict that "RLHF
  will cause sycophancy on your model" from first principles. It depends on the
  reward model, the base model's prior, the data distribution, and their
  interaction.
  2. No universal regression taxonomy — The table I gave you above is
  synthesized from dozens of papers, blog posts, and practitioner experience.
  There's no standardized ontology of "regression types" that a tool could
  reason over.
  3. Capability measurement is unsolved — To predict regression, you need to
  measure capability before and after. But many capabilities (spatial reasoning
  in VLMs, temporal coherence in video diffusion) lack reliable automated
  metrics.
  4. The design space is combinatorial — (base model) × (post-training method) ×
   (data mix) × (hyperparameters) × (target capability) is a massive space.
  Empirical lookup tables don't generalize; analytical models don't exist.

  My Honest Assessment

  This is a research-worthy project, not an afternoon hack. The closest analogy
  is how AutoML matured — it started as "just grid search hyperparameters" and
  evolved into NAS, learned optimizers, etc. A "Post-Training Regression
  Prevention" framework would follow a similar arc:

  - Phase 1: Curated lookup table (if you're doing X with model Y, watch out for
   Z — here's the mitigation). This alone would be valuable and is buildable
  today.
  - Phase 2: Empirical scaling laws for regression (how much replay data
  prevents forgetting as a function of fine-tuning data size, domain shift,
  etc.)
  - Phase 3: Predictive models that generalize across model families.

  Phase 1 is something you could build now — essentially an expert system / RAG
  system over the accumulated practitioner knowledge, with structured output.
  Would you want to explore building that?

⏺ Great question — let me be brutally honest about what's grounded vs. what's
  wishful thinking.

  ---
  Literature Landscape: Surprisingly Fragmented

  The literature exists but it's scattered across subfields that don't talk to 
  each other:

  Subfield: Catastrophic forgetting / Continual Learning
  Volume of Literature: Large (1000s of papers)
  Directly Applicable?: Partially — mostly studied on small CNNs/toy tasks, not
    modern LLM post-training. The gap between "EWC on MNIST permutations" and
    "preventing reasoning loss during DPO on Llama-3-70B" is enormous.
  ────────────────────────────────────────
  Subfield: RLHF failure modes
  Volume of Literature: Growing (50-100 key papers)
  Directly Applicable?: Yes — reward hacking, mode collapse, alignment tax are
    well-documented. But mostly descriptive ("we observed X"), not prescriptive
    ("do Y to prevent X").
  ────────────────────────────────────────
  Subfield: Quantization degradation
  Volume of Literature: Moderate (200+ papers)
  Directly Applicable?: Yes — this is the most predictable area. Perplexity vs.
    bit-width curves are well-characterized.
  ────────────────────────────────────────
  Subfield: Knowledge distillation gaps
  Volume of Literature: Moderate
  Directly Applicable?: Partially — capacity gap is studied but mostly in vision

    (teacher-student CNNs), less in LLM/diffusion contexts.
  ────────────────────────────────────────
  Subfield: Data mixing / replay
  Volume of Literature: Small but growing
  Directly Applicable?: Key papers exist (DoReMi, D4, Data Mixing Laws) but they

    optimize for pre-training loss, not post-training regression prevention
    specifically.
  ────────────────────────────────────────
  Subfield: LoRA/PEFT regression
  Volume of Literature: Small
  Directly Applicable?: Mostly empirical blog posts and a few papers (LoRA
  learns
    less and forgets less — Biderman et al. 2024). Not enough for predictive
    models.
  ────────────────────────────────────────
  Subfield: Diffusion model fine-tuning regressions
  Volume of Literature: Very small
  Directly Applicable?: Scattered across DreamBooth/textual inversion papers. No

    systematic study.
  ────────────────────────────────────────
  Subfield: VLM post-training regressions
  Volume of Literature: Very small
  Directly Applicable?: A handful of papers (LLaVA-series ablations, InternVL
    reports). Mostly buried in appendices.
  ────────────────────────────────────────
  Subfield: Cross-modal regression
  Volume of Literature: Almost nothing
  Directly Applicable?: This is frontier territory. No systematic framework.

  Bottom line: There's enough literature to build a useful Phase 1 system for
  LLMs + (SFT/RLHF/DPO/Quantization). For everything else, you're in
  "practitioner lore + scattered ablation studies" territory.

  ---
  The Honest Buildability Matrix

  This is the critical part — separating what's engineering from what's open 
  research from what's fundamentally unpredictable:

  Tier 1: Buildable Today (Engineering Problem)

  These have sufficient empirical grounding that a lookup + heuristic system
  works:

  Component: Quantization regression prediction
  Why It's Buildable: Near-deterministic — given model family + bit-width +
    method (GPTQ vs AWQ vs GGUF), degradation on standard benchmarks is
    predictable within ~2-3%
  Key Literature: GPTQ (Frantar et al.), AWQ (Lin et al.), SqueezeLLM, QuIP# —
    extensive benchmark tables exist
  ────────────────────────────────────────
  Component: Replay data ratio for SFT forgetting mitigation
  Why It's Buildable: Well-studied heuristic: 5-20% replay of pre-training-like
    data prevents most forgetting. Exact ratio depends on domain shift, but
  rough
     guidelines are reliable
  Key Literature: "Don't Stop Pretraining" (Gururangan et al. 2020), continued
    pre-training literature
  ────────────────────────────────────────
  Component: KL penalty strength for RLHF/DPO
  Why It's Buildable: Standard practice: β coefficient in DPO, KL penalty in
  PPO.
    Literature converges on working ranges per model scale
  Key Literature: InstructGPT, DPO paper (Rafailov et al.), Zephyr, Tulu
  ────────────────────────────────────────
  Component: LoRA rank/target module selection
  Why It's Buildable: Empirical guidelines are stable: rank 16-64 for most
  tasks,
    targeting attention projections. Higher rank → more capability retention,
    less efficiency
  Key Literature: LoRA (Hu et al.), QLoRA (Dettmers et al.), "LoRA Learns Less
    and Forgets Less" (Biderman et al. 2024)
  ────────────────────────────────────────
  Component: Eval suite generation for regression
  Why It's Buildable: You know the model type + training task → you can
    deterministically select which benchmarks to monitor
  Key Literature: Just mapping — no prediction needed, pure engineering

  Tier 2: Buildable With Caveats (Empirical Heuristics, Not Guarantees)

  These work on average but will be wrong for specific cases:

  Component: Predicting which capabilities degrade first
  What Works: General rule: rare/low-frequency capabilities degrade before
  common
    ones. Multilingual before English. Reasoning before fluency.
  What Doesn't: Can't predict specific capability cliffs — e.g., at what point
    CoT reasoning breaks
  Key Literature: Scaling laws literature, "Emergent Abilities" (Wei et al.),
    compression literature
  ────────────────────────────────────────
  Component: Data mix optimization
  What Works: DoReMi-style approaches can optimize training mix to minimize
    worst-domain loss. Directionally useful.
  What Doesn't: Optimizes for loss, not for capabilities. Low perplexity ≠
    preserved capability. The mapping from loss to downstream task performance
  is
     noisy and non-linear.
  Key Literature: DoReMi (Xie et al. 2023), Data Mixing Laws (Ye et al. 2024),
    Doremi-like approaches
  ────────────────────────────────────────
  Component: Reward model quality → RLHF regression risk
  What Works: Reward model accuracy on held-out preferences correlates with
    downstream alignment quality. You can flag "this RM is too weak for this
    task."
  What Doesn't: Reward hacking is adversarial — a 90%-accurate RM can still be
    catastrophically exploited on the 10% failure modes. You can't predict how
    it'll be hacked.
  Key Literature: "Scaling Laws for Reward Model Overoptimization" (Gao et al.
    2023)
  ────────────────────────────────────────
  Component: Gradient conflict detection
  What Works: PCGrad / CAGrad / gradient cosine similarity can flag conflicting
    objectives in the first few hundred steps. Cheap proxy for later regression.
  What Doesn't: False negatives — some regressions emerge only after thousands
  of
    steps when representation shift accumulates. Early gradients can look fine
    while late training diverges.
  Key Literature: PCGrad (Yu et al. 2020), CAGrad, "Gradient Vaccine"
  ────────────────────────────────────────
  Component: Representation drift monitoring (CKA)
  What Works: Comparing CKA similarity of intermediate representations
    before/after N steps flags structural drift. Cheap early warning.
  What Doesn't: Threshold calibration is model-specific. High CKA drift doesn't
    always mean regression. Low drift doesn't guarantee safety. It's a signal,
    not a verdict.
  Key Literature: CKA (Kornblith et al. 2019), various mechanistic
    interpretability work

  Tier 3: Fundamentally Hard to Predict (Open Research)

  These cannot be solved by lookup tables or heuristics — they require
  understanding we don't have:

  Component: Emergent capability loss
  Why It's Unpredictable: Capabilities emerge non-linearly at scale → they
    disappear non-linearly too. You can't predict that "fine-tuning for 500 more

    steps will break in-context learning" because the capability's mechanism
    isn't localized.
  State of Research: Active debate — some argue emergence is a mirage of metric
    choice (Schaeffer et al. 2023), others disagree. No resolution.
  ────────────────────────────────────────
  Component: Reward hacking specifics
  Why It's Unpredictable: The existence of reward hacking is predictable. The
    specific exploit the model finds is not — it depends on  the interaction
    between model capabilities and reward model blind spots, which is
    combinatorial.
  State of Research: Goodhart's Law is well-understood conceptually. But
    predicting the specific failure mode is equivalent to predicting adversarial

    examples, which is NP-hard in general.
  ────────────────────────────────────────
  Component: Cross-modal regression patterns
  Why It's Unpredictable: How vision-language binding degrades during text-only
    SFT depends on connector architecture, pre-training recipe, and data
    distribution in ways nobody has systematically mapped.
  State of Research: Basically no systematic literature. Each VLM paper reports
    its own ablations with no unified framework.
  ────────────────────────────────────────
  Component: Interaction effects between sequential post-training stages
  Why It's Unpredictable: Real pipelines do SFT → DPO → quantization → merging.
    Each step's regression interacts with previous steps' regressions in
    unpredictable ways.
  State of Research: Almost zero literature on compositions of post-training
    methods. Everyone studies methods in isolation.
  ────────────────────────────────────────
  Component: Long-tail knowledge preservation
  Why It's Unpredictable: Whether a specific rare fact survives fine-tuning
    depends on its representation in the network, which we can't inspect at
    scale. Aggregate statistics (perplexity) miss individual fact loss.
  State of Research: Knowledge neuron / fact localization research (Meng et al.,

    ROME/MEMIT) gives some tools but doesn't scale to "predict which of 10M
  facts
     will be lost."
  ────────────────────────────────────────
  Component: Diffusion model compositional generation regression
  Why It's Unpredictable: Whether "astronaut riding a horse on the moon"
  degrades
    after style fine-tuning depends on how composition is implemented in
    cross-attention, which isn't understood well enough to predict.
  State of Research: T2I-CompBench benchmarks exist but no predictive theory for

    when composition breaks.

  ---
  The Uncomfortable Truth

  What you can predict         What you can't predict
  before spending compute      before spending compute
  ─────────────────────        ─────────────────────────

  ✓ Quantization degradation   ✗ Which specific capability breaks
    (±2-3% on benchmarks)
                               ✗ When emergent abilities vanish
  ✓ Rough forgetting risk
    (high/medium/low)          ✗ How reward hacking manifests

  ✓ Which eval suite to run    ✗ Interaction effects across

  ---
  Why "Just Predict It" Is Deceptively Hard

  The request seems reasonable:

  INPUT:  base model + training method + data + target task
  OUTPUT: "change X, add Y, don't do Z"

  But this requires solving a chain of sub-problems, each of which is
  independently open:

  Sub-Problem 1: Mapping Weights → Capabilities

  To predict "this training run will break capability X," you need to know where
   capability X lives in the model. We don't.

  What we know:
    - Factual recall is somewhat localized (ROME/MEMIT found specific MLP
  layers)
    - Attention heads have identifiable roles (induction heads, etc.)

  What we don't know:
    - Where "multi-step reasoning" lives
    - Where "spatial understanding" lives in a VLM
    - Where "compositional generation" lives in a diffusion model
    - How any capability is distributed across layers

  Without this mapping, you cannot predict which capabilities
  a gradient update will damage.

  This is the mechanistic interpretability problem. Anthropic, DeepMind, and
  others are working on it, but we're years away from "given these weights, here
   are the capabilities and their locations."

  Sub-Problem 2: Predicting Gradient Trajectories

  Even if you knew where capabilities lived, you'd need to predict what the 
  optimizer will do to those regions given your data. This requires knowing:

  Given:
    - Initial weights W₀
    - Dataset D
    - Optimizer (AdamW, hyperparams)
    - N steps of training

  Predict:
    - Which weight regions shift
    - By how much
    - In what direction

  This is literally predicting the output of a chaotic
  dynamical system over thousands of steps.

  We can't do this. Even for linear regression, predicting the exact SGD
  trajectory over N steps with random mini-batches requires running it. For a
  billion-parameter model with nonlinear interactions, it's computationally
  irreducible — the cheapest way to know what training does is to train.

  Sub-Problem 3: Mapping Data Distribution → Training Dynamics

  Your ideal tool says "change these data points." But the mapping from:

  "remove 500 medical QA examples and add 200 code examples"
          ↓
  "reasoning capability preserved, domain knowledge maintained"

  ...is not a function we can evaluate without training. Data influence methods
  exist (TracIn, datamodels) but they:

  - Are computed post-hoc (require a trained model to trace back influence)
  - Scale as O(n × m) where n = data points, m = eval points
  - Are approximations that break for large distribution shifts

  Sub-Problem 4: The Evaluation Problem

  Even after training, we can't reliably measure many capabilities:

  Things we can measure well:
    ✓ Perplexity
    ✓ Multiple-choice benchmarks (MMLU, etc.)
    ✓ Constrained generation (code that passes tests)

  Things we can't measure well:
    ✗ "Does the model still reason about novel problems?"
    ✗ "Has the VLM's spatial understanding degraded?"
    ✗ "Is the diffusion model's compositional ability intact?"
    ✗ "Will this model hallucinate in deployment scenario X?"

  So even the feedback loop for building your predictive tool is broken — you'd
  need ground-truth regression labels to train a predictor, but you can't
  reliably generate those labels.

  ---
  Why This Isn't Like Other Engineering Problems

  You might think: "We predict material failure, bridge loads, chip behavior —
  why not neural network behavior?"

  The difference:

  Engineering Domain: Structural engineering
  Why Prediction Works: Governed by well-understood physics (stress-strain
    curves, material properties). Finite element analysis gives reliable
    predictions because the underlying equations are known.
  ────────────────────────────────────────
  Engineering Domain: Chip design
  Why Prediction Works: Circuit behavior is deterministic given the design.
    Simulation = reality (mostly).
  ────────────────────────────────────────
  Engineering Domain: Aerodynamics
  Why Prediction Works: Navier-Stokes equations are known. CFD simulations are
    expensive but accurate.
  ────────────────────────────────────────
  Engineering Domain: Neural network training
  Why Prediction Works: The "physics" is SGD on a loss landscape we can't
    characterize. The landscape changes with data, architecture, and scale in
    ways we have no closed-form description of. We don't have the equivalent of
    Maxwell's equations for neural network behavior.

  The honest analogy is weather prediction, not bridge engineering. We can
  predict "it will probably rain this week" (directional) but not "it will rain
  at 2:47 PM at this exact location" (precise). Similarly:

  - We can predict: "SFT on narrow data will cause some forgetting"
  (directional)
  - We cannot predict: "step 8,400 will break CoT reasoning on math problems
  with >3 steps" (precise)

  ---
  Why This Doesn't Exist Yet (The Real Reason)

  It's not a science problem. It's an incentive + coordination problem:

  1. Labs that have the data don't need the tool — they have internal tribal
  knowledge and can afford to iterate
  2. Practitioners who need the tool can't generate the data alone — each person
   trains 1-5 models, not 500
  3. Academics aren't incentivized — a "regression lookup table" isn't
  publishable at NeurIPS. It's not novel science. It's infrastructure.
  4. Fine-tuning-as-a-service companies could build this but they'd be giving
  away their competitive advantage

  1. Defines the schema (like the YAML above) — standardize what a "regression

  2. Seeds 50-100 high-value cells through systematic ablation runs on the most

  The Key Gap: Eval Scores

  The biggest problem is that most fine-tunes don't have standardized benchmark 
  results. Without the delta, you can't compute regression.

  But there are three ways to close this:

  Option 1: Compute Them Yourself

  For the top ~5000 most-downloaded fine-tunes on HF:
    - Pull model
    - Run LM Eval Harness (MMLU, GSM8K, HumanEval, etc.)
    - Compare to known base model scores
    - Store deltas

  Cost estimate:
    ~5000 models × ~30 min eval each on A100
    = ~2500 GPU-hours
    = ~$5K-7K on cloud compute

  This is very doable.

  Option 2: Leverage Existing Eval Runs

  Open LLM Leaderboard v1 had ~6000 models evaluated
  Open LLM Leaderboard v2 has ~3000+
  Many model cards contain eval results in structured format

  Cross-reference these with base model scores
  = instant regression data for ~5000-8000 models
  with zero additional compute

  Option 3: Community Contribution via TRL Callback

  # A TRL callback that auto-logs regression metrics
  # to the HF Hub after training

  class RegressionTracker(TrainerCallback):
      def __init__(self, base_model_id, eval_tasks):
          self.base_scores = load_base_scores(base_model_id)
          self.eval_tasks = eval_tasks

      def on_train_end(self, args, state, control, **kwargs):
          current_scores = run_eval(model, self.eval_tasks)
          deltas = {
              task: current_scores[task] - self.base_scores[task]
              for task in self.eval_tasks
          }
          # Auto-push to a central regression database
          push_regression_report(
              base_model=self.base_model_id,
              fine_tune=args.output_dir,
              method=infer_method(args),
              deltas=deltas,
              training_args=args.to_dict()
          )

  If this were integrated into TRL/Axolotl/LLaMA-Factory as a default-on
  callback, the data would accumulate organically.

⏺ The Minimal Full-Stack Post-Training Toolkit

  The goal: cover every post-training method across every foundation model type
  with the fewest libraries.

  ---
  The Brutal Minimum

  You need exactly 5 libraries to cover everything:

  1. transformers          (model loading, architecture access)
  2. trl                   (SFT, DPO, ORPO, KTO, PPO/RLHF, reward modeling)
  3. peft                  (LoRA, QLoRA, adapters, prefix tuning)
  4. diffusers             (diffusion model fine-tuning — image, video)
  5. auto-gptq OR autoawq  (quantization)

  + 2 infrastructure libraries:
  6. accelerate            (distributed training, mixed precision)
  7. datasets              (data loading, processing)

  That's it. 7 libraries cover ~95% of post-training.

  # Gradient ascent unlearning — the simplest approach
  # Literally just negate the loss on data you want to forget

  from transformers import Trainer

  class UnlearningTrainer(Trainer):
      def compute_loss(self, model, inputs, **kwargs):
          outputs = model(**inputs)
          # Negate the loss — gradient ASCENT on forget set
          return -outputs.loss

  # GDiff — the standard practical approach
  class GDiffTrainer(Trainer):
      def __init__(self, *args, forget_dataloader=None, **kwargs):
          super().__init__(*args, **kwargs)
          self.forget_iter = iter(forget_dataloader)

      def compute_loss(self, model, inputs, **kwargs):
          # Descent on retain set (normal)
          retain_loss = model(**inputs).loss

          # Ascent on forget set (negate)
          forget_batch = next(self.forget_iter)
          forget_loss = model(**forget_batch).loss

          return retain_loss - forget_loss

  # DPO-based unlearning — reuse TRL directly
  # Just format your data as:
  #   chosen = retain responses
  #   rejected = forget responses (things you want unlearned)
  # Then run DPOTrainer as-is

❯   Verdict: Unlearning doesn't need a library — it needs recipes. Most methods 
   are 10-50 lines on top of transformers + trl.                                
                                                              why so?           

⏺ Because unlearning is not algorithmically complex — it's a loss function 
  modification on top of the same training loop you already have.

  ---
  Why Unlearning Is "Just" a Loss Swap

  Every post-training method is fundamentally:

  loop:
    sample batch
    forward pass
    compute loss    ← THIS is the only part that changes
    backward pass
    optimizer step

  The entire training infrastructure — data loading, gradient computation,
  distributed training, checkpointing, mixed precision, logging — is identical.
  The only thing that differs between SFT, DPO, and unlearning is what scalar 
  you backpropagate.

  SFT:         loss = -log P(correct answer | input)
  DPO:         loss = -log σ(β · (log P(chosen)/P_ref(chosen) - log
  P(rejected)/P_ref(rejected)))
  Unlearning:  loss = +log P(forget answer | input)     ← literally negate SFT
  loss
  GDiff:       loss = -log P(retain) + log P(forget)     ← one addition

  There's no new optimizer, no new data loader, no new distributed strategy, no
  new architecture modification. You're changing one line in compute_loss.

  ---
  Then Why Does DPO Get a Library (TRL) But Unlearning Doesn't?

  Fair question. The answer is standardization pressure.

  DPO:
    - Thousands of people run it daily
    - Standard data format (chosen/rejected pairs)
    - Standard hyperparameters (β, learning rate ranges)
    - Standard eval (MT-Bench, AlpacaEval)
    - HF ecosystem wants one canonical implementation
    - Worth maintaining a Trainer class for

  Unlearning:
    - Tens of people run it, not thousands
    - No standard data format
      (what does "forget set" look like? a list of facts?
       a dataset? a capability description? all of the above?)
    - No standard hyperparameters
      (how hard do you push gradient ascent before the model
       collapses? nobody agrees)
    - No standard eval
      (how do you verify something is truly "forgotten" vs
       just suppressed? open research question)
    - The method itself is 10 lines but the PROBLEM DEFINITION
      is not standardized

  The reason unlearning doesn't have a library is not that the code is trivial.
  It's that:

  1. The Problem Definition Is Unstandardized

  "Unlearn medical knowledge" — what does this mean?

    Option A: Model outputs "I don't know" for medical questions
              → This is just safety fine-tuning, use DPO

    Option B: Model literally cannot generate medical text
              → Gradient ascent on medical corpus

    Option C: Model's internal representations no longer
              encode medical knowledge (extractable via probing)
              → Much harder, no method reliably achieves this

    Option D: A sufficiently motivated adversary cannot extract
              the knowledge through any prompting strategy
              → Formally unsolved, possibly impossible

  Every unlearning paper picks a different definition. A library would have to
  pick one, and there's no consensus.

  2. Evaluation Is Unsolved

  SFT: "Did accuracy go up on target task?" — measurable
  DPO: "Does the model prefer the right response?" — measurable
  Quantization: "Did perplexity change?" — measurable

  Unlearning: "Is the knowledge truly gone?"
    - Model says "I don't know" → maybe it's just refusing,
      knowledge is still there, jailbreak can extract it
    - Model fails on benchmarks → maybe it's forgotten,
      maybe it's just confused on the format
    - Probing classifiers can't find it → maybe you're
      probing the wrong layer
    - Membership inference says "not trained on it" →
      maybe the test is underpowered

  There is no reliable ground truth for "forgotten."

  3. The Hard Part Isn't The Training — It's The Data Curation

  For SFT:  "Here's a dataset" → train → done
  For DPO:  "Here's preference pairs" → train → done

  For unlearning:
    Step 1: Define exactly WHAT to forget
            (which facts? which capabilities? what granularity?)
    Step 2: Curate a "forget set" that covers it
            (how do you enumerate "all medical knowledge"?)
    Step 3: Curate a "retain set" that is the complement
            (everything else — how do you sample from "everything"?)
    Step 4: Balance forget vs retain pressure
            (too much forget → model collapses on everything
             too little forget → knowledge persists)
    Step 5: Verify it actually worked (see evaluation problem above)

  Steps 1-4 are the actual work. Step "train the model"
  is the trivial part.

  ---
  So What Would a Real Unlearning Library Need to Solve?

  It's not the training loop. It's everything around it:

  WHAT A REAL UNLEARNING LIBRARY WOULD LOOK LIKE:

  1. FORGET SET CONSTRUCTION
     - Input: "forget all knowledge about Person X"
     - Output: curated dataset of all text associated with Person X
     - Requires: entity linking, knowledge graph traversal,
       semantic search over training data (which you may not have)

     THIS IS THE HARD PART. Nobody has automated this.

  2. RETAIN SET CONSTRUCTION
     - Input: forget set + base model capabilities to preserve
     - Output: balanced retain set that anchors everything else
     - Requires: capability-aware sampling from general data

     THIS IS ALSO HARD. Same problem as the regression
     prevention we discussed — you need to know what to protect.

  3. UNLEARNING METHOD SELECTION
     - Gradient ascent vs GDiff vs DPO-based vs task arithmetic
     - Depends on: granularity (single fact vs broad capability),
       verifiability requirements, compute budget

     This could be a decision tree — not hard.

  4. HYPERPARAMETER CALIBRATION
     - How many steps of gradient ascent before collapse?
     - What learning rate avoids overshooting?
     - What forget/retain ratio?

     Model-specific, currently requires manual tuning.
     Could be partially automated with the HF regression
     database we discussed.

  5. VERIFICATION
     - Did unlearning work?
     - Is it robust to adversarial extraction?
     - Did retain capabilities survive?

     OPEN RESEARCH PROBLEM. No library can solve this.

  ---
  The Honest Summary

  What's trivial:        The training loop modification (10-50 lines)
  What's engineering:    Method selection, hyperparameter defaults
  What's hard:           Forget/retain set construction
  What's unsolved:       Verification that unlearning actually worked

  A library for unlearning would be 5% training code
  and 95% data curation + evaluation tooling.

  That's why it doesn't exist as a training library —
  because the bottleneck was never training.

  The real unlearning library that's needed looks less like TRL and more like a
  knowledge management + data curation + adversarial evaluation tool. The
  compute_loss is the least interesting part of the problem.

  This is also why regulators are struggling with "right to be forgotten" for
  LLMs — even the people building the models can't reliably verify that
  unlearning worked.

  The Actual Ranking (By Practical Usability)

  RANK 1: OpenUnlearning
    WHY: Only framework that consolidates methods + benchmarks +
         eval into one codebase. You can run 12 methods on 3
         benchmarks with one config file change.
    LIMITATION: Research code, not pip-installable. LLMs only.

  RANK 2: EasyEdit
    WHY: Most mature, most starred, multimodal support (VLMs).
         Best for surgical fact editing (ROME/MEMIT).
    LIMITATION: Unlearning is a secondary use case. Editing ≠ unlearning.
         Editing changes a fact, unlearning removes knowledge entirely.
         These are different goals with different verification requirements.

  RANK 3: SalUn
    WHY: Only method that bridges LLMs AND diffusion models.
         Saliency-guided approach is more principled than blind
         gradient ascent.
    LIMITATION: Single method, not a framework.

  RANK 4: UnlearnCanvas
    WHY: Only serious benchmarking framework for diffusion unlearning.
         10 methods compared. Nothing else covers this space.
    LIMITATION: Evaluation only, not a training framework.

  RANK 5: WMDP/RMU
    WHY: The safety community's standard. If your use case is
         "remove hazardous knowledge," this is the benchmark and
         baseline method.
    LIMITATION: Narrow scope (safety only). One method.

  Everything else: research repos tied to a single paper.

  ---
  The Critical Problem Nobody Has Solved

  The OPTML group at Michigan State published Unlearn-Smooth (ICML 2025) showing
   that:

  ▎ Almost all existing unlearning methods fail under relearning attacks — 
  ▎ fine-tune the "unlearned" model on a small amount of the forgotten data, and
  ▎  the knowledge comes back.

  This means:

  Current state of unlearning:

    Method claims: "Model has forgotten X"
    Reality:       "Model is SUPPRESSING X"

    Proof: 50-100 examples of X + 5 minutes of fine-tuning
           → knowledge is fully restored

    This is true for: GradAscent, GradDiff, NPO, DPO-based,
                       KL-based, and most other methods.

    Partial exceptions: RMU and SAM-enhanced methods show
                        more resistance, but not immunity.

  This is why I said earlier that verification is the unsolved part. The
  training loop is trivial. The methods exist. But none of them provably work in
   the sense that regulators or users actually need.

  The field has lots of libraries for doing unlearning. It has zero libraries
  for confirming unlearning actually happened.

  ---
  Where Each One Sits and Why

  Unsloth — Layer 3 (Kernel Optimization)

  What it does:
    Rewrites the actual CUDA kernels for attention, MLP,
    and LoRA backward passes to be 2-5x faster and use
    60-70% less memory.

  What it wraps:
    transformers + TRL + PEFT underneath.
    Your training script is still SFTTrainer/DPOTrainer.
    Unsloth patches the model's forward/backward at load time.

  What it adds:
    ✓ Custom Triton kernels (fused QLoRA, RoPE, cross-entropy)
    ✓ Memory reduction (train 70B on 80GB GPU that normally needs 2x)
    ✓ Gradient checkpointing optimizations
    ✓ 4-bit quantized training that's actually fast
    ✓ GGUF/GPTQ/AWQ export built-in

  What it doesn't add:
    ✗ No new training methods — same SFT/DPO/ORPO/PPO as TRL
    ✗ No new data processing
    ✗ No eval framework
    ✗ Limited model support (popular models only — Llama, Mistral,
      Qwen, Gemma, Phi. Not arbitrary architectures)

  Mental model:
    Unsloth is to TRL what Flash Attention is to standard attention.
    Same math, faster execution.

  Axolotl — Layer 3 (Configuration Orchestration)

  What it does:
    Wraps the entire training pipeline into a single YAML config.
    You don't write Python. You write config, run one command.

  What it wraps:
    transformers + TRL + PEFT + accelerate + DeepSpeed +
    Flash Attention + xformers + bitsandbytes

  What it adds:
    ✓ Single YAML config for any training run
    ✓ Every combination pre-wired (model × method × data format ×
      distributed strategy × quantization)
    ✓ Data format handling (ShareGPT, Alpaca, completion,
      chat templates — automatically detected)
    ✓ Multi-dataset mixing with weights
    ✓ Sample packing (multiple examples per sequence for efficiency)
    ✓ DeepSpeed ZeRO 1/2/3 configs included
    ✓ Weights & Biases / MLflow integration
    ✓ Resume from checkpoint

  What it doesn't add:
    ✗ No new training methods beyond what TRL provides
    ✗ No kernel optimizations (can use Unsloth as a backend though)
    ✗ No eval framework
    ✗ No model architecture changes

  Mental model:
    Axolotl is a Makefile for fine-tuning. It doesn't do anything
    you couldn't do in a Python script with TRL + PEFT. It just
    eliminates the boilerplate.

  ---
  When to Use What

  "I want maximum control and I write Python"
    → Raw TRL + PEFT + accelerate
    → You need this for: distillation, unlearning, custom losses,
      research, anything non-standard

  "I want the same thing but faster and on fewer GPUs"
    → Unsloth + TRL + PEFT
    → You need this for: single-GPU training, memory-constrained
      setups, rapid iteration, GGUF export
    → Trade-off: limited model support, less multi-GPU flexibility

  "I want to train many models with different configs without code"
    → Axolotl
    → You need this for: systematic sweeps, team workflows where
      non-engineers need to launch training, reproducibility
    → Trade-off: debugging YAML config errors is painful,
      less flexibility for custom methods

  "I want a web UI and I'm exploring"
    → LLaMA-Factory
    → You need this for: quick experiments, non-technical users,
      visual parameter tuning
    → Trade-off: least flexible, hardest to customize

  "I don't want to manage infrastructure"
    → HF AutoTrain or cloud APIs (Together, Fireworks, Modal)
    → Trade-off: least control, most expensive per run

  ---
  What's Actually Happening in Practice

  Most serious practitioners use a hybrid:

  Exploration/prototyping:
    Unsloth notebooks (fast iteration, single GPU)

  Production training:
    Axolotl YAML configs (reproducible, version-controlled)
    OR raw TRL scripts (when Axolotl can't express what you need)

  Multi-node large-scale:
    Raw TRL + accelerate + DeepSpeed ZeRO-3
    (neither Unsloth nor Axolotl handles this as well)

  Export/deployment:
    Unsloth (GGUF export) → llama.cpp / Ollama
    OR auto-gptq/autoawq → vLLM / TGI

  Anything weird (unlearning, distillation, custom losses):
    Raw transformers + TRL, no wrappers

  Unsloth and Axolotl don't expand what you can do — they make the common paths
  faster and easier. The moment you need something non-standard, you drop back
  to TRL.

  ---
  Where bitsandbytes Specifically Fits

  Without bitsandbytes:
    Load Llama-3-70B → needs ~140GB GPU memory (FP16)
    Train Llama-3-70B → needs ~280GB+ (weights + optimizer + gradients)
    = 4× A100-80GB minimum for just loading

  With bitsandbytes:
    Load in 4-bit (NF4) → ~35GB GPU memory
    QLoRA training → ~40-45GB (only LoRA gradients in full precision)
    = 1× A100-80GB for training a 70B model

  It's not a training method. It's not an optimizer.
  It's a MEMORY COMPRESSION LAYER that makes large-model
  post-training physically possible on fewer GPUs.

  The dependency chain for QLoRA specifically:

  Your training script
    └── TRL (SFTTrainer with peft_config)
         └── PEFT (LoraConfig)
              └── transformers (AutoModelForCausalLM.from_pretrained(
                     quantization_config=BitsAndBytesConfig(load_in_4bit=True)))
                   └── bitsandbytes (actual NF4 CUDA kernels)
                        └── CUDA

  If Unsloth is in the picture, it replaces the bitsandbytes backward pass with
  its own faster Triton kernels but still uses bitsandbytes for the initial
  4-bit weight loading. So even with Unsloth, bitsandbytes isn't fully
  eliminated — it's partially superseded.

  ---
  Three Distinct Reasons For Fragmentation

  Reason 1: The Science Isn't Settled

  For some domains, there's no standard post-training method because nobody 
  agrees on what works.

  LLMs:
    "How to fine-tune?" → SFT. Settled since 2022.
    "How to align?" → DPO/RLHF. Settled since 2023.
    "How to make efficient?" → LoRA. Settled since 2023.

    The methods converged → tooling consolidated around them.

  Video Generation:
    "How to fine-tune?" → LoRA on spatial layers? Temporal layers?
      Both? With what loss? On what data format? Frame-by-frame
      or clip-level? What resolution? What frame rate?

    Nobody agrees → every model repo tries something different
    → impossible to build a unified library when the interface
    isn't stable.

  Speech TTS:
    "How to clone a voice?" → Fine-tune decoder? Train adapter?
      Speaker embedding? In-context learning? Zero-shot?
      Codec-based? Spectrogram-based? End-to-end?

    The ARCHITECTURES are still diverging (codec vs mel vs e2e)
    → can't standardize post-training when the models themselves
    aren't standardized.

  ---
  Reason 3: The Abstraction Boundaries Are Wrong

  This is the subtle one. HuggingFace's abstraction works for LLMs because:

  LLM ABSTRACTION:

    model.forward(input_ids) → logits
    loss = cross_entropy(logits, labels)

    This interface is IDENTICAL for every LLM.
    GPT-2, Llama-3, Mistral, Qwen — same signature.

    So TRL can write ONE SFTTrainer that works for all of them.

  This abstraction breaks for other model types:

  VLM ABSTRACTION PROBLEM:

    LLaVA:    model.forward(input_ids, images) → logits
              images go through CLIP → projection → interleaved with text tokens

    Qwen-VL:  model.forward(input_ids, images) → logits
              images go through ViT → resampler → special <img> tokens

    InternVL: model.forward(input_ids, pixel_values, image_flags) → logits
              dynamic resolution, variable number of image tiles

    "Same signature" but the DATA PREPROCESSING is completely different.
    How images become tokens, how many tokens per image, how multi-image
    inputs are handled — all different.

    A unified Trainer would need to abstract over the data pipeline,
    not just the forward pass. Nobody has done this well.


  DIFFUSION ABSTRACTION PROBLEM:

    SD 1.5:   unet(latent, timestep, text_embedding) → noise_pred
    SDXL:     unet(latent, timestep, text_embedding, added_cond_kwargs) →
  noise_pred
    SD3:      transformer(latent, timestep, text_embedding1, text_embedding2,
                           text_embedding3) → flow_pred
    Flux:     transformer(latent, timestep, text_embedding, guidance) →
  flow_pred

    The forward signature changes with EVERY major model.
    UNet vs DiT. Noise prediction vs flow matching vs velocity prediction.
    1 text encoder vs 2 vs 3.

    diffusers handles this by having model-specific training scripts,
    not a unified Trainer. That's why there's train_dreambooth_sdxl.py
    AND train_dreambooth_flux.py — separate scripts, not one configurable one.


  SPEECH TTS ABSTRACTION PROBLEM:

    XTTS:     model(text, speaker_embedding) → mel_spectrogram → vocoder →
  waveform
    F5-TTS:   model(text, reference_audio) → waveform (end-to-end)
    VALL-E:   model(text, acoustic_prompt) → audio_codec_tokens → decoder →
  waveform
    Parler:   model(text, description) → audio_codes → DAC decoder → waveform

    The OUTPUT MODALITY is different. Some output spectrograms, some
    output codec tokens, some output waveforms directly.

    You can't write a unified Trainer when the loss function
    depends on the output representation.

  ---
  What Would Unification Actually Require?

  For each model type, the missing piece is different:

  VLMs:
    Missing: STANDARDIZED MULTIMODAL DATA FORMAT

    If every VLM agreed on "this is what a training example
    looks like" (like how LLMs agreed on chat templates),
    a unified Trainer becomes possible.

    HF is trying with chat templates that include images:
      {"role": "user", "content": [{"type": "image"}, {"type": "text", "text":
  "..."}]}

    But the vision preprocessing (how many tiles, what resolution,
    what normalization) is model-specific and can't be abstracted away.

    FIXABLE? Partially. Data format: yes. Vision preprocessing: no,
    it's architecture-dependent.


  Image Diffusion:
    Missing: UNIFIED TRAINING LOOP ACROSS ARCHITECTURES

    The gap between UNet (SD 1.5/SDXL) and DiT (SD3/Flux) models
    is too large for one Trainer. But within each family, unification
    is possible.

    FIXABLE? Yes, once architecture converges to DiT.
    diffusers + finetrainers are heading this direction.


  Video:
    Missing: EVERYTHING

    Architecture, method, data format, eval — all unstandardized.

    FIXABLE? Not yet. Need architecture convergence first.
    finetrainers is the earliest attempt.


  Speech:
    Missing: ARCHITECTURE CONVERGENCE

    Can't unify fine-tuning when models output different representations.

    FIXABLE? Possibly converging toward codec-based models
    (SpeechTokenizer, EnCodec). If this becomes standard,
    TTS fine-tuning becomes "just LLM fine-tuning on codec tokens"
    and the LLM stack (TRL) becomes applicable.
    This is actually starting to happen.

  ---
  The Prediction

  NEXT 2-3 YEARS:

  1. VLMs will absorb into the LLM stack
     - Already happening: TRL's SFTTrainer works with VLMs now
     - Chat template standardization for multimodal is progressing
     - lmms-eval is maturing
     - Remaining gap: vision preprocessing stays model-specific

  2. Image diffusion will consolidate around DiT + diffusers
     - kohya is adding Flux/SD3 support
     - diffusers is absorbing kohya patterns
     - The two camps will merge as UNet models fade

  3. Video will follow image diffusion with ~2 year lag
     - finetrainers is the seed
     - Once DiT-based video models dominate, diffusers
       training scripts will extend naturally

  4. Speech TTS will become "LLM fine-tuning on codec tokens"
     - The codec-LM architecture (VALL-E, SpeechGPT, etc.)
       turns TTS into a sequence-to-sequence problem
     - At that point, TRL + PEFT just work
     - NeMo will remain the enterprise alternative

  5. Audio generation will follow the same codec-LM path

  6. Any-to-any multimodal will remain fragmented the longest
     - Requires ALL of the above to converge first

  The pattern is: everything is becoming a transformer, and everything is 
  becoming a token prediction problem. As that happens, the LLM post-training
  stack (transformers + TRL + PEFT) becomes the universal stack by default — not
   because HuggingFace planned it, but because the architectures are converging
  toward the same abstraction.

  The scatter you're seeing today is a transitional phase. The domains where
  architecture has converged (LLMs, embeddings) have unified tooling. The
  domains where it hasn't (speech, video, multimodal) are fragmented. As each
  domain's architecture settles, the tooling will consolidate — not because
  someone builds a unified library, but because the models themselves become
  similar enough that one library covers them.

    - More diverse benchmark suite (200+ tasks in lm-eval)
    - Harder benchmarks exist (MATH-500, GPQA, LiveBench)
      that aren't saturated yet
    - Community adds new benchmarks as old ones saturate
      (this is an active practice — MMLU → MMLU-Pro,
       GSM8K → MATH → AIME)

    Revised: 70% (not 90%)
    The tooling is there. The benchmark hygiene is not.

  ---
  The Benchmark Treadmill Problem

  This is the underlying structural issue:

  Timeline of a VLM benchmark:

  Year 0: Benchmark created. SOTA scores 40%.
          Lots of headroom. Useful for detecting regression.

  Year 1: Better models. SOTA scores 65%.
          Still useful but smaller delta for regression detection.

  Year 2: SOTA scores 80%.
          Benchmark is "solved" for practical purposes.
          Fine-tuning regressions of 3-5% are within noise.

  Year 3: Benchmark deprecated / ignored.
          Community moves to harder benchmark.

  Problem: New harder benchmark exists but:
    - Not yet integrated into lmms-eval
    - Not yet used as standard regression check
    - Has its own problems (small n, domain-specific)
    - 2-3 year lag before it becomes standard

  This cycle means eval always lags model capability.
  For regression detection specifically, you're always
  evaluating on benchmarks that are slightly too easy
  for current models.

  ---
  What A Good VLM Regression Suite Would Look Like

  Given saturation, a useful post-training regression suite would:

  1. USE HARD BENCHMARKS WITH HEADROOM
     - MMMU-Pro (harder than MMMU)
     - MathVista (visual math reasoning)
     - OCRBench (document understanding)
     - BLINK (visual perception tasks humans find easy)

  2. TEST AT THE CAPABILITY BOUNDARY, NOT AVERAGE
     Instead of "average VQAv2 score", test:
     - Hardest 20% of questions only
     - Questions the base model got right by <60% margin
     - Out-of-distribution visual inputs

  3. INCLUDE CROSS-MODAL ALIGNMENT PROBES
     - Winoground (compositional)
     - MMVP (fine-grained visual detail)
     - MMRel (visual relationship reasoning)

  4. MINIMUM SAMPLE SIZE PER DOMAIN
     Most benchmarks have 50-200 samples per capability.
     At 3-5% regression detection, you need 500+ samples
     to be statistically meaningful.

  5. GENERATION NOT JUST COMPREHENSION
     Standard VLM benchmarks test multiple choice / VQA.
     But fine-tuning regressions often show up in generation
     quality first. Need captioning + description + analysis
     tasks with quality metrics.

  None of this exists as a packaged suite you can just run. It's the VLM
  equivalent of the LLM regression framework problem from earlier in our
  conversation — the data and benchmarks exist piecemeal, nobody has assembled
  them into the right pipeline.

  Key Design Decisions

  - Benchmarks chosen for headroom — MMVP (SOTA 38%), Winoground (SOTA 28%),
  MathVista (SOTA 63%) all have large room to detect regressions before
  saturation. VQAv2 deliberately excluded.
  - Caching — each (model, benchmark) pair cached to JSON so partial runs resume
   instead of starting over
  - GPU cleanup — base model explicitly deleted and CUDA cache cleared before
  loading fine-tuned model
  - Lazy imports — datasets/torch/transformers only imported when actually
  needed, so CLI --help works without ML stack installed
  - Severity thresholds — CRITICAL (>10%), HIGH (5-10%), MEDIUM (3-5%), LOW
  (1-3%) mapped to the fact that these benchmarks aren't saturated, so small
  deltas are meaningful
