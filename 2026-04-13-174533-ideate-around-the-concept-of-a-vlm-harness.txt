⏺ VLM Harness — Ideation

  Core Concept

  A VLM harness is a standardized framework for evaluating, benchmarking, and
  testing Vision Language Models across diverse visual understanding tasks.
  Think of it as what lm-evaluation-harness (EleutherAI) is for text LLMs, but
  purpose-built for the multimodal visual domain.

  ---
  Why it's needed

  - Fragmented evaluation landscape — VLM benchmarks (MMMU, MMBench, SEED-Bench,
   VQAv2, etc.) each have their own data formats, prompting conventions, and
  scoring logic. Researchers rewrite boilerplate for every new benchmark.
  - Inconsistent methodology — Different papers use different prompt templates,
  image resolutions, and decoding strategies for the same benchmark, making
  cross-model comparisons unreliable.
  - Rapid model proliferation — GPT-4o, Claude, Gemini, LLaVA, Qwen-VL,
  InternVL, Phi-Vision... new VLMs ship weekly. A unified harness lets you
  evaluate any model on any benchmark with a single config change.

  ---
  Key Design Dimensions

  1. Task Taxonomy

  vlm-harness/
  ├── perception/          # Low-level visual understanding
  │   ├── ocr              # Text recognition in images
  │   ├── object_detection # Localization + classification
  │   ├── spatial          # "What's to the left of X?"
  │   └── counting         # "How many dogs?"
  ├── reasoning/           # Higher-order inference
  │   ├── chart_qa         # Reading charts/graphs
  │   ├── diagram          # Scientific/technical diagrams
  │   ├── math_visual      # Geometry, visual word problems
  │   └── multi_image      # Cross-image reasoning
  ├── knowledge/           # World knowledge grounded in vision
  │   ├── landmark         # Place recognition
  │   ├── cultural         # Cultural context understanding
  │   └── domain_specific  # Medical, satellite, etc.
  ├── generation/          # Output quality beyond classification
  │   ├── captioning       # Image description fidelity
  │   ├── grounded_qa      # Answers traceable to image regions
  │   └── creative         # Visual storytelling
  └── safety/              # Refusals, bias, hallucination
      ├── hallucination     # Does the model invent objects?
      ├── bias              # Demographic fairness in descriptions
      └── adversarial       # Jailbreaks via visual injection

  2. Model Interface — The Adapter Pattern

  The harness shouldn't care whether the model is an API, a local HuggingFace
  model, or a custom inference server.

  class VLMAdapter(Protocol):
      def generate(
          self,
          images: list[Image],          # PIL / path / URL
          prompt: str,
          system: str | None = None,
          max_tokens: int = 1024,
          temperature: float = 0.0,
      ) -> VLMResponse: ...

      def supports_multi_image(self) -> bool: ...
      def supports_video(self) -> bool: ...
      def max_image_resolution(self) -> tuple[int, int] | None: ...

  Ship adapters for: openai, anthropic, google-genai, huggingface
  (transformers), vllm, ollama, litellm.

  3. Benchmark as Data, Not Code

  Each benchmark is declared, not programmed:

  # benchmarks/mmmu.yaml
  name: MMMU
  source: huggingface://MMMU/MMMU
  splits: [validation, test]
  task_type: multiple_choice
  prompt_template: |
    {question}
    Options: {choices}
    Answer with the letter only.
  image_fields: [image_1, image_2, image_3]  # which columns have images
  answer_field: answer
  metrics: [accuracy, accuracy_by_subject]

  This makes adding a new benchmark a YAML file, not a PR with 200 lines of
  Python.

  4. Scoring & Metrics

  Go beyond simple accuracy:

  ┌──────────────────────┬──────────────────────────────────────────────────┐
  │        Metric        │                 What it measures                 │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Exact match /        │ Standard MC / extraction tasks                   │
  │ accuracy             │                                                  │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ LLM-as-judge         │ Open-ended answer quality (configurable judge    │
  │                      │ model)                                           │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ CHAIR                │ Hallucinated object rate in captions             │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Spatial IoU          │ Bounding box / region accuracy                   │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Refusal rate         │ Safety-sensitive prompts                         │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Consistency          │ Same answer across paraphrased prompts           │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Cost & latency       │ $/question, p50/p95 latency                      │
  └──────────────────────┴──────────────────────────────────────────────────┘

  5. Image Pipeline

  One of the trickiest parts — models handle images very differently:

  - Resolution normalization — Some models tile, some resize. The harness should
   log the actual pixels sent.
  - Multi-image ordering — Interleaved vs. all-images-first matters.
  - Augmentation probes — Run the same benchmark with rotated/cropped/compressed
   images to test robustness.
  - Region annotations — Support for bounding boxes, masks, and visual prompting
   (e.g., "the circled object").

  6. Hallucination Detection (Differentiator)

  This is the killer feature that doesn't exist well today:

  vlm-harness eval --model claude-opus-4-6 --benchmark hallucination-probe

  Results:
    Object hallucination rate:     3.2%
    Attribute hallucination rate:  7.1%
    Spatial hallucination rate:   11.4%
    "I can't tell" calibration:   0.89  (closer to 1.0 = better)

  Build a curated dataset of images with ground-truth object inventories, then
  measure how often models invent things that aren't there.

  ---
  CLI / UX Vision

  # Evaluate a model on a benchmark
  vlm-harness eval --model anthropic:claude-opus-4-6 --bench mmmu --split val

  # Compare two models head-to-head
  vlm-harness compare --models openai:gpt-4o,anthropic:claude-opus-4-6 --bench
  vqav2

  # Run the full safety suite
  vlm-harness eval --model local:llava-next --suite safety

  vlm-harness serve --results-dir ./results --port 8080

  vlm-harness add-bench --from hf://lmms-lab/SEED-Bench-2

  ---
  Open Questions / Tensions

  1. Video support? Many VLMs now accept video. Does the harness scope to still
  images only, or handle video benchmarks (ActivityNet-QA, Video-MME) from the
  start?
  2. Interactive / agentic tasks? Some VLM evals are multi-turn (e.g., "click
  the button" in VisualWebArena). That's a fundamentally different execution
  model — include or punt to v2?
  3. Closed vs. open benchmarks — Test sets with hidden answers (like MMMU-test)
   require server-side scoring. Support submission-based workflows or focus on
  locally-scorable splits?
  4. Cost tracking — For API models, tracking $/eval is essential for
  practitioners. Bake it in or leave it to the adapter?
  5. Reproducibility — Should the harness pin image hashes and prompt templates
  in a lockfile so results are exactly reproducible months later?

  ---
  Differentiation from Existing Tools

  The pitch: vlm-harness is the pytest of VLM evaluation — minimal, composable,
  benchmark-as-config, adapter-based, with first-class hallucination and safety

  Now addressing your feedback — great points, all three:

  1. 3D Vision Problems

  The current taxonomy is entirely 2D. A proper VLM harness should include:

  - Depth estimation — monocular depth from single images
  - 3D spatial reasoning — "which object is closer to the camera?", "could you
  reach X from Y?"
  - Novel view synthesis understanding — given one view, reason about what
  another view would show
  - Point cloud / mesh comprehension — for models that accept 3D inputs
  (emerging)
  - Scene reconstruction reasoning — "how would this room look from the
  doorway?"
  - Benchmarks like ScanQA, 3DMV-VQA, SQA3D, and Objaverse could slot in here

  2. True Cross-Modal Reasoning

  The taxonomy treats vision and language as "image in, text out" — but real
  multimodal understanding requires simultaneous processing where neither
  modality alone is sufficient:

  - Visual entailment — does the image support/contradict the text claim?
  - Cross-modal retrieval — given an interleaved document (text + figures +
  tables), answer questions that require synthesizing across all of them
  - Audio-visual (for models that support it) — "what is the person saying?"
  from video+audio
  - Interleaved document reasoning — research papers, textbooks, webpages where
  figures are referenced in text and both must be understood together
  - Diagram-to-code — understanding a visual representation and producing
  structured output that proves joint comprehension

  3. Borrowing from LLM Harness

  Absolutely — lm-evaluation-harness has battle-tested components that should be
   reused rather than rebuilt:

  - Text-only metrics (BLEU, ROUGE, perplexity, exact match, F1) — identical
  implementations
  - Few-shot example selection — the sampling strategies are modality-agnostic
  - Answer extraction / normalization — regex-based extractors for MC, numbers,
  etc.
  - Logging and result serialization — the output format and aggregation logic
  - Task grouping and suite management — how benchmarks compose into suites

  The ideal approach might be to make vlm-harness an extension of
  lm-evaluation-harness rather than a fork — inheriting its text pipeline and
  adding the vision pipeline on top.

  ---
  On running evaluations against CLIP, BLIP, LLaVA, and recent VLMs:

  The harness is now built and all unit tests pass. However, actually running a
  benchmark evaluation against these models has a few hard requirements:

  1. Model weights must be downloaded — LLaVA, BLIP-2, InternVL2, etc. are
  multi-GB downloads from HuggingFace. CLIP is smaller but still requires
  transformers + torch.
  2. Benchmark data must be accessible — MMMU, VQAv2, etc. download from
  HuggingFace Datasets on first use (also several GB).
  3. GPU strongly recommended — running inference on LLaVA-13B or InternVL2-8B
  on CPU is impractically slow.

  The harness supports all of these out of the box. Once you have the
  environment set up, the commands would be:

  # Install HuggingFace backend
  pip install vlm-harness[huggingface]

  # LLaVA-1.6 on MMMU (100 samples to test)
  vlm-harness eval \
    --model huggingface:llava-hf/llava-v1.6-mistral-7b-hf \
    --bench mmmu --split validation --max-samples 100

  # BLIP-2
  vlm-harness eval \
    --model huggingface:Salesforce/blip2-opt-2.7b \
    --bench vqav2 --split validation --max-samples 100

  # InternVL2, Qwen-VL, Phi-3-Vision (recent models)
  vlm-harness eval --model huggingface:OpenGVLab/InternVL2-8B --bench mmmu
  vlm-harness eval --model huggingface:Qwen/Qwen2-VL-7B-Instruct --bench chartqa
  vlm-harness eval --model huggingface:microsoft/Phi-3.5-vision-instruct --bench
   textvqa

  CLIP is image-text matching only (no generation), so it doesn't fit the
  standard generate() interface — it would need a dedicated adapter. Want me to
  build a CLIPAdapter that adapts CLIP's similarity scores to work with yes/no
  and retrieval benchmarks?
